# Decisions

Answers to the spec's open questions, plus implementation choices made while building. Each entry says what was chosen and why. Entries are append-only.

## From the spec's open questions

1. **Name and license.** Crate `code-explorer-mcp` (the name `code-explorer` is taken on crates.io), binary `code-explorer`, GitHub repo `code-explorer-mcp`. License MIT.
2. **Worker cap vs per-key throttling.** v1 has a global concurrency cap only, as the spec recommends. No per-key limit, not even optional. Authenticated traffic is never rate limited.
3. **Key hashing.** argon2id kept (m=19456 KiB, t=2, p=1), with the 10 minute verified-key cache so the cost is paid once per key per window.
4. **History depth.** Default 200 commits.
5. **Author emails.** Off by default (`logging.author_emails = false`).
6. **Staleness.** A stale snapshot is a notice on results, never a refusal. No hard cutoff.
7. **Repo ids as an enum per key.** Kept. `tools/list` injects the caller's allowed repo ids as an enum on every `repo` and `repos` parameter.
8. **Legacy protocol window.** Clients on 2025-11-25 and earlier are served without sessions through rmcp's compatibility mode. No drop date in v1.
9. **Templates such as `.env.example`.** Denied by default. Operators carve exceptions with `[deny] allow`.
10. **Image distribution and signing.** v1 ships the Dockerfile and compose files. CI builds the image to prove it builds but does not push. Registry publishing, signing and SBOM are later work.
11. **Bitbucket plan check.** Operator responsibility, documented in the README: repository access tokens may be unavailable on some plans, in which case SSH access keys are the fallback.

## Implementation choices

- **MCP SDK.** rmcp 3.5 with `transport-streamable-http-server`, mounted in axum as a Tower service. Stateless (`NeverSessionManager`), `legacy_session_mode = false`, `json_response = true`. rmcp's own Host and Origin checks are disabled; the server enforces Origin itself so the rule lives in one place and applies before auth.
- **Authentication context.** The axum auth middleware inserts an `AuthContext` into the HTTP request extensions. rmcp copies `http::request::Parts` into the MCP request extensions, so every tool reads the key name and allow-list from `ctx.extensions`. A tool call without an `AuthContext` fails closed with an internal error.
- **Per-key tool list.** `ServerHandler::list_tools` is written by hand: it takes the router's tool list and rewrites the `repo` and `repos` schemas with the caller's repo ids as an enum.
- **Config error reporting.** Syntax and unknown-field errors come from `toml` with their span. Semantic problems are collected into a list and each is given a line number by looking the key path up in a `toml_edit` document parsed from the same text.
- **Credentials and git.** HTTPS tokens reach git through `GIT_ASKPASS` pointing at the server binary itself (`code-explorer askpass`, a hidden subcommand). The helper reads the secret from a file named in `CODE_EXPLORER_ASKPASS_FILE`. Credentials given by env var are written once at start to a 0600 file in a private temp dir so the same path is used. SSH keys use `GIT_SSH_COMMAND` with `IdentitiesOnly=yes`, `StrictHostKeyChecking=yes`, `BatchMode=yes` and a pinned `known_hosts` file.
- **Subprocess safety.** Every `git`, `rg` and `gitleaks` child runs with a cleared environment, in its own process group, under a timeout; on expiry the whole group is killed. A global semaphore caps concurrent children.
- **Snapshot cleanup.** A `Snapshot` removes its worktree directory when the last reference to it is dropped, so in-flight calls always finish on the snapshot they started with.
- **Scanner.** gitleaks `dir` mode over the new worktree plus a file holding the commit messages of the kept history. Secret values live only in memory, inside the redactor.
- **Durations.** `humantime` syntax in TOML (`"5m"`, `"30s"`, `"2h"`).
- **Metrics.** The `prometheus` crate with a dedicated registry served as text on the admin listener.
- **Scanner hardening.** gitleaks honours `.gitleaks.toml`, `.gitleaksignore` and `gitleaks:allow` comments found in the scanned tree, which would let a repo hide its own findings. The adapter always passes its own default ruleset with `--config`, an empty `--gitleaks-ignore-path` and `--ignore-gitleaks-allow`.
- **Scan runs.** gitleaks does not follow a symlinked directory, so the worktree and the commit-message file are scanned in two parallel runs and the findings merged. Commit-message fingerprints are `commit_messages:<rule>:<line>`.
- **Remote URL refresh.** The bare repo keeps the clone-time origin URL, so the puller runs `git remote set-url origin` before every fetch and a config change to path, host or credential type takes effect at the next tick.
- **Clone staging.** A clone lands in `git.clone/` and is renamed to `git/` on success, so a crash mid-clone leaves nothing a later fetch would trip on.
- **state.json trust.** On restore, a worktree path outside `snapshots/` or containing `..` is rejected. Stored findings go through the allowlist again, and a repo under the block policy is rescanned.
- **SSH first.** The owner's repos are reached over git SSH only. SSH deploy keys (GitHub) and repository access keys (Bitbucket) are the documented default in the example config, the compose secrets and the onboarding steps. HTTPS tokens stay supported as the second option because the project is generic.
- **Public repos.** A repo entry may omit `credential` for anonymous HTTPS access to a public repo. SSH always needs a key.
- **Keys file polling.** inotify on the parent directory does not see writes to a Docker bind-mounted file, and a watch on the file itself survives neither an atomic replace nor a mount of a new inode. The key store therefore also polls the file's mtime and length every 2 seconds. Found when `keygen` from a second container did not trigger a reload in the serving container.
- **Compose subnet.** The compose network subnet is `EDGE_SUBNET` in `.env` (default `172.30.0.0/24`) and must match `server.trusted_proxies`. Found when the default overlapped an existing network on the build machine.
- **keys.toml is read-only to the server.** The lead's review of milestone 3 rejected making the bind-mounted keys file writable by the server's uid: a compromised server could then mint itself a key that survives restarts. The compose file mounts it `:ro`, the server never writes it (only `keygen` does, as an operator command), and `keygen --print-only` writes the `[[key]]` entry to stdout and the key to stderr so `>> keys.toml` on the host is the documented flow.
- **Trusted proxies are explicit.** `server.trusted_proxies` defaults to `[]`. In the compose profile Caddy has a fixed address (`CADDY_IP`, default `172.30.0.2`) and only that `/32` is trusted. Trusting the whole subnet would also trust the bridge gateway (`.1`), which is how clients on the Docker host reach the published port, and any of them could then set `X-Forwarded-For` to dodge the failed-attempt throttle. A trusted proxy that sends no usable client address is logged at most once a minute per proxy, and `check-config` warns when `trusted_proxies` is set with an empty `client_ip_header`.
- **Throttle reset.** A successful authentication does not clear failures inside the window; it only removes an entry whose block has expired, as the spec says. Earlier builds cleared the counter on any success, which let a client holding one valid key interleave it with guesses.
- **Bounded key verification.** Disabled and expired keys are rejected before any hashing. Argon2 runs under a semaphore (`auth.max_concurrent_verifications`, default 4); a request that cannot get a slot within 2 seconds receives 503 `busy` with `Retry-After: 2` and is not counted as a failed attempt. Failures that need no hashing (missing, malformed, unknown id, disabled, expired) are recorded before any verification work, and the block is checked again once a slot is acquired.
- **Connection hygiene.** Each listener closes a connection after 60 seconds without bytes in either direction, pings idle HTTP/2 connections every 20 seconds, and accepts at most `server.max_connections` (default 1024, minimum 16) at a time; the next connection is accepted and closed at once. An HTTP/2 client that answers pings but never sends a request is bounded only by the connection cap.
- **Admin listener default.** `admin_listen` stays `0.0.0.0:9090` because the container needs it, and `check-config` warns whenever it is not loopback: the endpoints are unauthenticated and the port must never be published.
- **Config type errors.** When the typed parse fails, a second pass checks each top-level section, each key of the defaulted sections, each `[[repo]]` entry and each credential on their own, so one run lists every bad value with its line. Semantic validation (paths, secrets, cross-references) runs only once the types are right, because validating a config with failed sections replaced by defaults produces misleading follow-on problems.
- **Supply chain.** CI actions are pinned to commit SHAs, the Rust builder image to a manifest digest, and CI runs `cargo audit` and `cargo deny` (advisories and licenses).
- **Redaction at rest.** Redacting only the strings a tool returns left the raw secret in the worktree that ripgrep searches, so `grep` became an oracle: match presence, `count` mode and `files` mode answered "does the secret start with AKIAQ?" one character at a time without ever printing it. Under the `redact` policy the snapshot build therefore rewrites the worktree itself: every indexed file up to `limits.max_file_bytes` that is not binary (no NUL in the first 8 KiB) is read whole, every occurrence of every found value is replaced with `[REDACTED:<rule_id>]`, and the file is written back in place without following symlinks. All values are applied to all files, not only the file gitleaks named, because the same value often appears elsewhere. A multi-line secret (a private key) becomes one marker per line so line numbers, permalinks and blame ranges stay aligned with the commit. The index size of each rewritten file is updated, and the worktree shows as modified to git, which is harmless because it is a detached checkout that is never committed or pushed. The in-memory redactor stays as a second wall for what is not on disk (commit messages, history read with `read_file` at a commit) and now also holds each line of a multi-line secret (trimmed, at least 6 bytes, PEM armor lines excluded) so per-line output is masked. The `warn` policy serves the raw worktree. Values that gitleaks found by decoding base64, hex or percent-encoding are redacted as the encoded text found on that line.
- **state.json holds no secret values.** It stores `state_version`, the commit, `findings` as `rule_id` and `fingerprint` only, `redacted_at_rest`, the paths of the rewritten files and `history_scanned`. A file with another `state_version` (including every file written before this change) is ignored and the snapshot is rebuilt from git. On restore the worktree is already redacted, so only the commit messages (and the history when `features.file_at_commit` is on) are rescanned to rebuild the in-memory redactor, and only when the stored findings are not empty. A stored snapshot that does not match the current config (raw worktree under `redact`, history never scanned while `file_at_commit` is on) is rebuilt.
- **History scan.** With `features.file_at_commit` on, `read_file` can serve any commit of the kept history, so the snapshot scan also runs `gitleaks git` over the bare repo from the tip (`--diff-merges=first-parent`, so content introduced by a merge itself is seen; the shallow boundary commit shows its whole tree). Its findings feed the redactor and the policy, so `block` holds on them too. A history finding whose value is already a worktree finding is dropped, so one value counts once and allowlisting it at the tip covers its copies in history; a value that exists only in history is allowlisted by its gitleaks fingerprint `<commit>:<path>:<rule>:<line>`. The puller and the `scan` command share `puller::prepare_scan_inputs` and `scan::scan_snapshot`, so onboarding reports exactly what serving would act on.
- **Scanner ruleset.** `[extend] useDefault = true` also inherits gitleaks' global path allowlist (node_modules, images, PDFs, lock files, minified vendor JS), and gitleaks has no way to drop an inherited allowlist. Those files are still served by `grep` and `read_file`, so the adapter embeds gitleaks v8.30.1's default config (MIT, license kept beside it in `src/gitleaks.LICENSE`) with the global `paths` list removed; the global value regexes and stopwords that suppress placeholders stay. The file is named `gitleaks.toml` so a gitleaks scan of this repository skips its regex fragments. UTF-16 files are not scanned by gitleaks; they contain NUL bytes, so `read_file` already treats them as binary, and the index marks files with a UTF-16 byte order mark (`FileIndex::is_utf16`) for the search path to skip.
- **Held tips.** When the block policy holds a commit, the repo reports `stale` (with `stale_seconds` counted from the last successful pull) while it keeps serving the previous snapshot, and the held tip is remembered: later pulls that fetch the same tip skip the checkout and the rescan and keep the hold. A new tip is scanned again.
- **No GitHub Actions.** The owner does not want GitHub CI. The proof is `scripts/check.sh` (fmt, clippy, tests, cargo audit, cargo deny, gitleaks over the tracked tree and the full history), run locally before every release. The workflow written earlier was removed before publication.
- **Bitbucket SSH host.** Bitbucket Cloud serves Git over SSH from `ssh.bitbucket.org` and keeps `bitbucket.org` for HTTPS, web and API, with `bitbucket.org` SSH ending on November 12, 2026 (Atlassian community announcement, and BCLOUD-24132 for the Pipelines known_hosts gap). SSH remotes are built with `Host::ssh_host()` (`ssh.bitbucket.org`), HTTPS remotes and permalinks keep `Host::domain()` (`bitbucket.org`), and the shipped `known_hosts` carries both hosts, whose keys are identical.
